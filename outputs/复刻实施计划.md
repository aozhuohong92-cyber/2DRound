# 《航海冒险》复刻实施计划

目标：尽量复现所提供 APK 的画面、交互与玩法。这里的“复现”分为视觉一致、流程一致、客户端规则一致、服务端结果一致四个层次；安装包分析与录屏能覆盖前三项的一部分，不能证明未知服务端逻辑完全相同。


## 本次分析后的第一批具体任务

1. 优先人工恢复 `base/baseclass`、`battle/battle_model`、`backpack/backpack_controller`，以及《待恢复代码清单》中的其他 7 个脚本。
2. 用 `main.lua`、`file_update.lua`、`module_include.lua` 确定同名模块变体的实际加载顺序；先固定包内版本，另记录登录后的更新差异。
3. 已验证 1,808 个可读脚本路径、1,054 个 CSB 路径；继续恢复动态拼接的图片/动画路径，处理 51 个尚未命名的 CSB 和未识别素材。
4. 从 `proto_mate.lua`、ProtoMgr 与 GameNet 提取消息字段，优先建立登录/角色/背包/战斗所需的离线响应。静态扫描得到 1,333 个不同的协议注册 ID，不要求首版全部实现。
5. 按 `config_init.lua` 的 720×1280 竖屏设计尺寸建立对照场景。验收顺序：主界面 → 角色 → 队伍 → 战斗 → 结算。
6. 同步审查生成代码中的 slot/uv 引用和条件表达式。2,136 个 Lua 文件语法通过，不能替代运行时语义验证。

## 推荐路线

先沿用 Cocos2d-x 3.13.1 + Lua/LuaJIT + Cocos Studio CSB + Spine 3.4 资源格式建立兼容性验证项目。不要在验证前升级 Spine 资源版本或重做全部界面。旧工具链仅用于恢复基线；能否用现代 Android 构建链发布，作为独立验证任务处理。

建议先做“离线可玩的竖切样例”：启动 → 主界面 → 角色页 → 布阵 → 单场战斗 → 结算 → 本地保存。它可以验证引擎、UI、动画、数值和资源路径是否真正打通。

服务端技术尚未从 APK 确认。先定义客户端需要的接口并实现本地 Mock，后续再根据并发、部署和团队经验选择后端语言与数据库，不把推荐技术冒充原游戏技术。

## 分阶段工作与验收

| 阶段 | 工作 | 可交付物与验收 |
|---|---|---|
| 1. 样本固定与代码恢复 | 保存哈希、清点 APK；导出 Android 代码；解码 Lua；记录失败与局限 | 文件清单、代码目录、可复跑脚本、逐文件状态；不能只交付后缀被改成 .lua 的二进制 |
| 2. 模块与资源对照 | 整理入口、模块、事件、协议、配置；建立哈希文件名与原始路径映射；解析 CSB 引用 | 模块依赖表、资源索引、界面状态表；随机抽查引用均可定位 |
| 3. 最小运行工程 | 恢复 Lua 绑定、文件加载、屏幕适配、Spine 动画、CSB 加载和字体音频 | 在目标 Android 真机上显示一个原始界面并播放一个完整角色动画；原生自定义 API 有替代实现 |
| 4. 离线战斗闭环 | 主界面、角色页、编队、关卡、技能演出、结算与本地存档 | 一条完整流程可玩；相同初始数据下结果可重复；录屏逐项对照 |
| 5. 系统补全 | 按脚本和录屏确认角色养成、背包、装备、招募、任务、活动等实际模块 | 每个模块都有入口、正常流程、空状态、资源不足、上限、返回流程验收 |
| 6. 自建后端 | 根据协议定义账户、角色、背包、关卡、任务、战斗结算等服务；实现数据持久化和配置版本 | 重登数据一致；并发请求不重复发奖/扣资源；客户端显示与服务端状态一致 |
| 7. 一致性与打包 | 固定设备分辨率、游戏版本和状态，核对界面位置、动画时序、数值变化、音效与操作 | 对照视频、差异清单、可安装测试 APK、构建说明；明确仍不能验证的服务端内容 |

## 原生代码恢复策略

Android Java 反编译结果可直接用于阅读接口，但缺少原始 Gradle、依赖版本、源码注释，不能认作可直接编译的完整项目。对 JNI、资源加载、SmartSocket、语音等 C++ 扩展建立接口清单：通用引擎部分用对应开源源码对照；定制部分根据符号、汇编与 Lua 调用点重建，逐项验证行为。

优先恢复对启动和战斗必需的原生接口。登录平台、语音、分享、支付等功能在离线样例中先用明确的本地实现或占位状态，不让不相关 SDK 阻塞主流程。后续需要的线上功能再接入自己的服务。

## 实施顺序与估算原则

先完成阶段 2–3 的技术验证，再给全量排期：脚本中是否存在未恢复函数、CSB 与 Spine 是否正常加载、自定义原生接口多少、服务端规则缺多少，都会显著影响工期。当前不承诺“拿到反编译代码就能直接生成一模一样的游戏”。

建议拆成可独立验收的小里程碑：一个界面 → 一个角色 → 一场战斗 → 一个养成闭环 → 一条重登持久化流程 → 逐模块扩展。每轮以同一组录屏和固定状态截图检查，不靠印象验收。

## 需要用户提供的材料

详见《试玩录屏清单.md》。优先前三段即可开始对照；更深层玩法等模块恢复清单明确后补录。若有原项目、服务端、配置表、管理后台导出或不同版本 APK，它们比单纯增加试玩时长更有价值。

## 当前无法仅靠 APK 确认的事项

- 原服务器语言、部署结构、数据库和完整业务源码。
- 服务端控制的真实掉落概率、匹配机制、反作弊、活动时间表和隐藏规则。
- 登录后下载的补丁、远程配置、动态活动资源是否与包内一致。
- 反编译代码的全部语义是否与运行时等价，需要实际验证。
- 原工程的完整目录、构建设置、未打包素材、历史修改和源码注释。
